# Secure Communications Infrastructure — PKI, mTLS, VPN, Firewall

> End-to-end secure communications stack built around an internal ECC-based PKI: HTTPS reverse proxy with Nginx, Flask web application with TOTP 2FA, PostgreSQL with mutual TLS authentication, OpenVPN for remote access, and nftables firewall enforcement.

📄 **[Read the full technical report (PDF)](docs/report.pdf)**

**Academic project** — Communications and Cybersecurity course, MSc in Informatics Engineering, University of Coimbra (2025/2026).
**Authors:** João Dias, Francisco Queirós

---

## Overview

This project implements a complete defensible communications infrastructure from scratch, following security design principles defined in a prior threat model. Every service in the stack authenticates via certificates issued by an internal Certificate Authority, all traffic is encrypted in transit, and access to the application is controlled by 2FA. The firewall and VPN enforce network-level isolation.

The full design rationale, test plan, and validation evidence is documented in the [technical report](docs/report.pdf).

## Architecture

```

│  Certificate Authority (ECC P-521)                              │
│  └── issues certificates to all services (ECC P-384) + CRL      │
└────────────────────────┬────────────────────────────────────────┘
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
       ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  OpenVPN     │  │  Nginx       │  │  PostgreSQL  │
│  TCP/1194    │  │  HTTPS :443  │  │  TLS :5432   │
│  TLS 1.3     │  │  TLS         │  │  mTLS        │
└──────────────┘  │  terminates  │  │  verify-full │
                  └──────┬───────┘  └──────▲───────┘
                         │ (loopback)      │
                         ▼                 │
                  ┌──────────────┐         │
                  │  Flask App   │ ────────┘
                  │  127.0.0.1   │  (mTLS client cert)
                  │  :5000       │
                  │  TOTP 2FA    │
                  └──────────────┘

  Firewall (nftables): default-deny, expose 443/1194 only
```

## Key technical decisions

| Decision | Choice | Rationale |
|---|---|---|
| CA algorithm | ECDSA secp521r1 (P-521) | Strong root, smaller signatures than RSA-4096 |
| Service cert algorithm | ECDSA secp384r1 (P-384) | Sufficient for service identity, faster handshake |
| Web exposure | Nginx reverse proxy, Flask on loopback | TLS termination at one place; reduces app's attack surface |
| DB authentication | mTLS with `sslmode=verify-full` | Client identity from certificate, not just password |
| DB access | Two roles (`webapp`, `readonly`) with separate certs | Privilege separation at the certificate layer, not just app logic |
| Password storage | `crypt()` via pgcrypto (server-side) | Hashing happens in the trusted DB, not at the app |
| 2FA | TOTP via pyotp + QR code provisioning | RFC 6238 standard, works with any authenticator app |
| VPN cipher | `AES-256-GCM:CHACHA20-POLY1305` | AEAD ciphers, no fallback to legacy modes |
| VPN DH | `dh none` | Modern OpenVPN with ECDH from cert; no static DH params needed |
| Firewall posture | `policy drop` on input + forward | Default-deny; only explicitly allowed traffic enters |

## Web application highlights

The Flask app (`web/app.py`) is small but exercises several non-trivial security features:

- **Two database connection profiles** — read/write operations use the `webapp` certificate; read-only queries use a separate `readonly` certificate. Privilege separation is enforced at the TLS layer, before any SQL is run.
- **TOTP-based 2FA** with QR-code enrollment (`/2fa/setup`, `/2fa/enable`, `/2fa/verify`).
- **Session-based auth** with a `login_required` decorator and explicit logout.
- **REST endpoints** alongside the HTML routes (`/api/news`, `/api/users`).
- **No client-side hashing** — passwords are validated server-side via `crypt()` from pgcrypto.

## Verification

The included `verify-complete-setup.sh` walks through the full setup and checks:

1. CA certificate exists and has `CA:TRUE` set
2. All service certificates are issued by the expected CA
3. Each certificate matches its private key
4. CRL is valid and lists revoked serials
5. nftables ruleset loads without errors
6. PostgreSQL accepts only TLS connections, rejects plaintext
7. SHA-256 checksums of all PKI artifacts match the baseline

A summary of the validation evidence (server-side `pg_stat_ssl` showing client certificate DN, OpenVPN logs showing `VERIFY OK` for client cert chain, listening ports audit, etc.) is in Section 4 of the report.

## What I learned

- **mTLS with PostgreSQL is fiddly but worth it.** The hardest part is matching the certificate's CN to the database role: `sslmode=verify-full` is meaningless if `pg_hba.conf` doesn't actually enforce certificate-based authentication.
- **Reverse proxies simplify the threat model.** Terminating TLS at Nginx and binding Flask to `127.0.0.1` means a developer mistake (e.g. accidentally enabling Flask debug mode) doesn't expose the app to the network.
- **`dh none` is the right modern default for OpenVPN.** Static DH parameters were a workaround for old TLS; with TLS 1.3 and EC-based key exchange from certificates, they're obsolete.
- **A `.gitignore` is a security control, not a convenience.** Half of the work for this repo was deciding what *not* to publish — keys, CSRs, the CA's index/serial state, the issued certs themselves.
